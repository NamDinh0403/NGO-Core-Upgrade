# ingest

The **single shared ingestion phase** for a new NGO Core release. Used by both
[backend](../backend/) and [frontend](../frontend/)
instead of each track independently re-reading the same Core git history and the
same shared `release-notes.md`.

## Why this exists

Before this module, each track had its own copy of "read the local NGO.Core git
tags/diffs, parse release-notes.md, cross-check, write a candidate" — meaning a
client upgrade that touches both backend and frontend did that work **twice**,
against the same repository and the same notes file, and could produce two
candidate records that quietly disagreed with each other. `ingest` does it
**once** per Core version and writes **one** shared, per-version record both
tracks read from.

## What it is not

- Not a client-mutating tool. Read-only against the local NGO.Core checkout.
- Not authoritative knowledge. Every record under `knowledge/candidates/` is a
  **candidate** (`status: "CANDIDATE"`) — a developer reviews and promotes it
  into each track's own `knowledge/canonical/` before it's trusted the way
  approved knowledge is.
- Not a replacement for the decompiled-installed-DLL rule
  (`backend/config/knowledge-priority.yaml#evidenceOverride`) or Core's
  own git history check (`frontend/config/knowledge-priority.yaml`) for
  a concrete symbol-signature question on the client's own restored packages.
  This module answers "what changed release-to-release and why", not "what does
  this symbol look like right now".

## Structure

```
ingest/
├── config/core-repository.yaml     Canonical config: Core repo path source, tag
│                                   convention, release-notes.md location, safety rules.
├── schemas/
│   ├── release-finding.schema.json     One evidence-backed finding (scope, source, crossCheck).
│   └── ingested-release.schema.json    One version's full candidate record (backend/frontend/shared sections).
├── tools/
│   ├── lib/
│   │   ├── git.js         Read-only git helpers: fingerprint, listTags, diffNameStatus.
│   │   ├── classify.js    Generic changed-file-path -> {scope, category} classifier.
│   │   └── notes.js       release-notes.md splitter (by version heading, by blank-line "card").
│   └── ingest.js          CLI: `check` (list newer tags) and `ingest` (produce a candidate record).
└── knowledge/
    └── candidates/
        └── releases/
            └── <version>.json   One shared candidate record per version. Never hand-edited;
                                  regenerated by `tools/ingest.js ingest`. Never canonical.
```

## Usage

```
# Proactively check for newer Core releases than either track's canonical knowledge knows about:
node ingest/tools/ingest.js check --core-path <path to local NGO.Core clone>

# Produce (or refresh) a candidate record for a specific version boundary:
node ingest/tools/ingest.js ingest --core-path <path> --release-notes <path to release-notes.md> --target 9.2.1
```

Both `backend/skills/ingest-core-release` and
`frontend/skills/ingest-core-release` invoke this CLI internally rather
than re-implementing git-diff/notes-parsing themselves; each then reads only its
own domain's section (`backend` / `frontend`) from the resulting record, plus the
`shared` section for cross-cutting items (deployment, pipeline, SQL scripts).

## Record shape (one file per version)

```jsonc
{
  "schemaVersion": 1,
  "version": "9.2.1",
  "status": "CANDIDATE",
  "ingestedAt": "2026-09-05T09:00:00Z",
  "sources": { "coreRepoPath": "...", "releaseNotesPath": "...", "tagRange": { "from": "v9.2.0", "to": "v9.2.1" } },
  "findings": {
    "backend": [ /* release-finding.schema.json items, scope: backend */ ],
    "frontend": [ /* scope: frontend */ ],
    "shared": [ /* scope: shared — deployment, pipeline, SQL, cross-cutting */ ]
  },
  "unresolvedItems": [ "..." ],
  "nextAction": "Developer: review, then promote applicable findings into each track's knowledge/canonical/."
}
```
