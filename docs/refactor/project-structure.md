## Cleanup Assessment

1. Review abandoned test runs first. Names such as `orchestrator-test-*` and `client-ngmodule/testrun` are candidates, not proof that evidence is disposable. Check their state and whether anyone needs them for reproduction or resume.
2. Archive finished client runs outside the source checkout only after retention and ownership review. Backend retention currently says 365 days. Preserve state, checkpoints, plans, reports, evidence, and rollback snapshots together; do not delete `pre-mutation/` backups piecemeal.
3. Shared ingest candidates dominate disk use. They are regenerable but currently tracked release evidence, not disposable client caches. Any pruning or external storage proposal must preserve the manifest, release identity/integrity checks, requested version coverage, and offline behavior.
4. Consolidate completed refactor documents only after reviewing inbound links. The root README links to the optimization report. Historical inventories are snapshots, not deletion authority.
5. Keep the four ownership modules: ingest (shared release facts), orchestrator (coordination), backend and frontend (client mutation). Their config, schemas, templates, skills, knowledge, tests, and CLI wrappers have distinct responsibilities.
6. Consider one test-directory convention across tracks as a later structural refactor. Today backend tests live mostly under tools, frontend mixes tests and tools, ingest uses tools, and orchestrator uses tests. Moving them requires import, validation-runner, and documentation updates.
7. Do not remove folders solely because they are empty or files solely because their contents match. Required layout policies, dynamic discovery, per-run initialization, and relative links may depend on them.

Recommended sequence: review test artifacts; archive eligible client runs; decide release-evidence storage policy; consolidate historical docs; only then consider source-layout changes. None of these actions were performed by this audit.
